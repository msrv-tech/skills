# Изолированный UI-worker 1С

UI-runner находится в полном `codex-test-bridge.cfe` и требует режим
совместимости базы-менеджера не ниже `8.3.12`. Целевая конфигурация может быть
старее: в неё устанавливается `codex-test-bridge-legacy.cfe`, она запускается
как `/TestClient`, а `/TestManager` работает в отдельной ИБ с полной сборкой.

Full-сборка не назначает `DefaultRoles`, поскольку такое переопределение
запрещено в режимах до `8.3.14`. Запускай UI-worker под выделенным пользователем
тестовой ИБ с достаточными правами.

`ui_worker.py` запускает штатные процессы тестирования 1С без окон на рабочем
столе пользователя. Это не pixel automation: действия с формами выполняет
объектная модель `/TestManager`, а worker отвечает за изоляцию и жизненный цикл.

## Backends

- `windowsDesktop` — отдельный невидимый Win32 desktop. Рекомендуется для ЗУП и
  других Windows-зависимых конфигураций.
- `xvfb` — отдельный X server для Linux-клиента 1С.
- `process` — обычные процессы для диагностики и CI-тестов самого worker;
  графические приложения в этом режиме не изолированы.
- `auto` — `windowsDesktop` на Windows, `xvfb` на Linux.

Процессы test client и test manager запускаются в одном desktop/display. Worker:

1. запускает `clientCommand`;
2. проверяет, что клиент не завершился в течение `startupDelaySeconds`;
3. создаёт задание `uiJobCreate` в HTTP bridge;
4. запускает `managerCommand` с `/TestManager` и идентификатором задания;
5. ждёт завершения менеджера и забирает `uiJobGet`;
6. удаляет задание, завершает оба процесса и удаляет изолированный desktop.

На Windows worker сначала отправляет окнам принадлежащих ему процессов штатный
`WM_CLOSE` и ждёт выхода до 15 секунд. `TerminateProcess` используется только
как fallback. Это важно для клиент-серверных баз: жёсткое завершение TestClient
во время фоновой стартовой операции может оставить серверный сеанс.

По умолчанию worker добавляет к обеим командам 1С ключи
`/DisableStartupDialogs /DisableStartupMessages /DisableSplash`, даже если они
не указаны в JSON. Отключение требует явного `"suppressStartupUi": false`.
После подключения встроенный менеджер закрывает только безопасные стартовые
диалоги с кнопками `Продолжить`, `ОК`, `Закрыть`, `Пропустить`, `Позже` и
`Отмена` (и английскими эквивалентами). `Да`, `Нет`, запись, проведение и
завершение работы автоматически не нажимаются.

Окна с кнопками `Перезапустить` / `Завершить работу` только фиксируются в
диагностике. Автоматический перезапуск включается явно параметром сценария
`"restartTestClientOnStartup": true`: одинаковый набор кнопок используется и
для прикладных блокировок входа, где перезапуск создаёт цикл.

Параметр `probeTestPort: true` включает активную проверку открытия TCP-порта.
Для штатного `/TestClient` она по умолчанию выключена: пробное подключение не
должно вмешиваться в протокол платформы, а порядок запуска test client и test
manager штатно может быть произвольным.

## Запуск

Для серверной ИБ скопируй `ui-worker.server.example.json`. Универсальный шаблон
лежит в `ui-worker.example.json`. Для старой целевой конфигурации используй
`ui-worker.cross-db.example.json`, а при наличии прикладного списка пользователей
— `ui-worker.cross-db.credentials.example.json` с существующими тестовыми
пользователями. Все файлы содержат только ссылки на переменные
окружения и не содержат адресов, путей или учётных данных:

```powershell
python .\client.py run-ui `
  .\server.example.invalid.json `
  .\examples\native-ui-smoke.ui.json `
  --artifact-dir .\artifacts\ui-smoke `
  --report .\artifacts\ui-smoke\worker.json
```

`--base-url` CLI не нужен: адрес опубликованного HTTP bridge задаётся в
`bridgeBaseUrl` файла worker. HTTP используется только как headless control
plane для передачи JSON-задания и результата; UI выполняет нативный клиент 1С.
Пароль перед запуском передаётся только через окружение:

```powershell
$credential = Get-Credential
$env:CODEX_1C_USERNAME = $credential.UserName
$env:CODEX_1C_PASSWORD = $credential.GetNetworkCredential().Password
```

Если значение нужно передать неинтерактивно, установи обычную переменную среды
в защищённом контексте CI. Worker подставляет её через
`environmentPlaceholders`. В отчёте всегда маскируются значения после `/P`,
`/N`, `/S`, `/F`, `--password`, `--user`, `--server` и `--database-path` —
локальная конфигурация не может случайно отключить эту защиту.

При загрузке доступов из `test-databases.json` в Windows PowerShell обязательно
задавай `Get-Content -Encoding UTF8`. Иначе кириллический логин повреждается до
запуска 1С. Credentials-шаблон пишет отдельный диагностический `/Out` в
`{clientLog}` внутри каталога артефактов.

Не коммить `server.example.invalid.json`, `.env`, отчёты, снимки и fixture-файлы. Эти
маски включены в `.gitignore` проекта.

## Placeholders конфигурации

- `{runId}` — уникальный ID запуска;
- `{jobId}` — идентификатор задания в регистре bridge;
- `{scenario}` — абсолютный путь переданного сценария;
- `{artifactDir}` — абсолютный каталог артефактов;
- `{clientLog}` — отдельный диагностический лог запуска TestClient;
- `{testPort}` — порт штатного `/TestClient`.

Подставляются только placeholders-идентификаторы. Обычные фигурные скобки в
BSL, Python и JSON остаются без изменений.

## Встроенный test manager CFE

Менеджер находится целиком в `CodexTestBridge.cfe`. Модуль управляемого
приложения расширяет `ПриНачалеРаботыСистемы` и включается только при `/C`,
начинающемся с `CodexUITest`:

```text
/TestManager /C "CodexUITest;Job={jobId};Host=127.0.0.1;Port=1538"
```

Он получает JSON-сценарий из регистра `CodexUIJobs`, подключается к тест-клиенту
штатным объектом `ТестируемоеПриложение` и сохраняет машинный результат обратно
в этот регистр. Это работает при безопасном режиме расширения: файловый доступ
TestManager не требуется. Внешние обработки и сторонние фреймворки не используются.

### Старая целевая конфигурация

В режиме совместимости `8.3.8` платформа запрещает расширению переопределять
модуль управляемого приложения. Понижение режима полного CFE поэтому не решает
задачу. Штатный путь — разделить процессы:

- `clientCommand` подключается к проверяемой базе с legacy bridge;
- `managerCommand` подключается к служебной тестовой базе с полным bridge;
- оба процесса находятся в одном скрытом desktop и связываются через порт
  `/TestClient`;
- JSON-задание и результат хранятся в базе-менеджере.

Если база присутствует в приватном `test-databases.json`, предпочтителен
`scripts/run_ui_from_test_database.py`: он запускает TestClient и TestManager
под существующим пользователем из реестра, передаёт секреты только через
переменные окружения процесса и не создаёт пользователей в базе. Для одной
целевой и управляющей базы допустим один и тот же тестовый пользователь.

Если сохранённые тестовые доступы неактуальны, используй
`scripts/run_cross_db_ui_with_bootstrap.py --allow-bootstrap-user`. Скрипт через
уже работающие HTTP bridge создаёт в обеих тестовых базах случайных скрытых
пользователей со всеми ролями, запускает тест без пароля и удаляет пользователей
в `finally`. Механизм предназначен только для изолированных тестовых баз.

Bootstrap создаёт пользователя платформы, но не объект прикладного списка
пользователей. Если конфигурация запрещает автоматическую регистрацию в БСП,
нужен существующий прикладной тестовый пользователь и credentials-шаблон.
Не используй bootstrap как обычный путь для БП и других конфигураций, где новый
пользователь запускает первичное заполнение или обновление: принудительное
завершение такого TestClient может оставить серверный сеанс обновления и
заблокировать следующие входы.

Нативный TestManager дополнительно закрывает главное окно TestClient, нажимает
только точную кнопку `Завершить работу` при её появлении и разрывает тестовое
соединение. Это поведение включено по умолчанию параметром сценария
`closeTestClientOnFinish`; перед закрытием worker успевает сохранить снимок.
Диалог `Авторизация не выполнена` — функциональный блокер, а не заставка; кнопка
`Завершить работу` намеренно не нажимается. Прикладным preflight управляют
`dismissStartupDialogs`, `startupDialogAttempts`, `startupDialogButtons` и
`startupSettleSeconds` сценария.

На Windows `scripts/build_cfe_windows.ps1` предпочитает `ibcmd`. Если компонент
`ibcmd` не установлен, скрипт автоматически использует пакетный Designer в
отдельном скрытом Win32 desktop через `scripts/build_cfe_designer_hidden.py`.
Сборка выполняется во временной файловой базе и не открывает окна на рабочем
столе пользователя.

Поддерживаемые нативные действия:

- `assertConnected` — smoke-проверка соединения с `/TestClient`;
- `openNavigationLink` — открыть `e1cib/...` напрямую через
  `ВыполнитьКоманду()` главного окна. Обязательный `targetForm` должен содержать
  `formName`, `objectName` или `title`: шаг успешен только после открытия именно
  этой новой формы. Форма ошибки навигации завершает шаг ошибкой;
- `openForm` — открыть форму объекта метаданных штатным клиентским
  `ОткрытьФорму()`, без подбора `e1cib`-ссылки. Передай `metadataKind`
  (`catalog`, `document`, `task`, `dataProcessor`, `report` или `commonForm`),
  `metadataName`, `formName` (кроме `commonForm`) и обязательный `targetForm`;
- `openDataProcessor` — короткая форма `openForm` для обычной обработки:
  передай `metadataName`, при необходимости `formName` и обязательный
  `targetForm`;
- `openTaskExecutionForm` — открыть назначенную для `ЗадачаИсполнителя` форму
  выполнения через штатный API `ФормаВыполненияЗадачи()`. Передай `uuid`, при
  необходимости `metadataName`, и обязательный `targetForm`. Не заменяй этот
  шаг кликом по декорации перехода;
- `executeCommand` — низкоуровневое выполнение навигационной команды окна;
- `inspectCommandInterface` / `clickCommandInterface` — прочитать или нажать
  штатную кнопку командного интерфейса активного окна. Это работает как с
  главным интерфейсом, так и с командной панелью открытой формы, которую
  `click` не обязан представлять как `ТестируемаяКнопкаФормы`. Для ранее
  сохранённой формы передай `form` и селектор `button`; bridge сначала
  активирует эту форму, затем ищет `ТестируемаяКнопкаКомандногоИнтерфейса`.
  Это семантический путь TestClient, без UIA, координат и догадок по кнопке.
  Обычный `click` по умолчанию также сначала ищет одноимённую штатную команду
  активной формы и лишь затем визуальную кнопку формы. Это нужно для команд,
  у которых `ТестируемаяКнопкаФормы.Нажать()` не вызывает обработчик. Для
  явного выбора пути задай `clickMode: "form"`, `clickMode: "command"` или
  `clickMode: "uia"`. UIA не использует координаты и выполняется отдельным
  ограниченным по времени worker-процессом; его нельзя автоматически сочетать
  с другим способом нажатия, чтобы не выполнить команду дважды.
- `waitForm` — найти форму и сохранить её под `saveAs`;
- `waitFormClosed` — дождаться закрытия ранее сохранённой формы;
- `waitElement` / `assertElement` — ожидать или проверить наличие, видимость,
  доступность и режим «только просмотр»;
- `activateForm`;
- `activateElement` — активировать поле, кнопку, таблицу или группу;
- `inspectUi` — получить дерево окна или сохранённой формы с типами,
  `objectName`, `title` и `formName`;
- `inspectTable` — получить фактические ключи колонок и значения выбранной
  строки `ТестируемаяТаблицаФормы`;
- `inputText` — ввод в поле формы;
- `selectReference` — выбрать настоящее ссылочное значение через штатный
  `ТестируемоеПолеФормы`;
- `selectFromDropdown` — низкоуровневый выбор точного или первого значения из
  выпадающего списка;
- `setCheckbox` — установить или снять флаг;
- `openChoice` — открыть кнопку выбора поля и сохранить появившуюся форму;
- `expandTreeRow` — найти строку дерева по `row` и раскрыть её штатной
  клавишей Right, без координат. Для поиска потомка можно вместо отдельного
  шага передать `expandParents: [{...}, {...}]` в `selectTableRow` или
  `assertTableRow`: родители раскроются по порядку до поиска строки;
- `pressKey` — отправить явную клавишу активному окну через изолированный UIA
  helper (поддерживаются стрелки, Enter, Space и F1…F12). Используй только для
  документированных shortcuts команды, когда платформа не публикует её в
  TestClient; это не координатный клик и не содержит конфигурационных веток;
- `selectTableRow` — перейти к строке таблицы по значениям колонок и выбрать её;
- `assertTableRow` — проверить наличие или отсутствие строки;
- `inputTableCell` — изменить текущую ячейку с корректным входом и выходом из
  режима редактирования строки;
- `click` — штатное нажатие кнопки формы;
- `assertField` — сравнение отображаемого значения поля;
- `handleDialog` — найти модальный диалог и нажать указанную кнопку. Для
  системного `MessageBox` bridge ищет кнопку в форме, активном окне и его
  командном интерфейсе; выбор всё равно должен быть указан явно через
  `dialogButton`, автоматического ответа «Да»/«Нет» нет;
- `closeForm` — закрыть форму, при необходимости обработав запрос сохранения
  через `onPrompt: discard|save|cancel`; отсутствие кнопки формы «Закрыть»
  определяется за одну секунду, после чего используется команда окна.

UI-сценарий намеренно не содержит переменных, циклов, условий, fixtures и
cleanup. Подготовка данных, запросы, проверки состояния БД, повторы сценариев и
очистка остаются в серверном bridge и `scenario_runner.py`; UI-worker исполняет
только атомарные действия TestClient.

Во всех шаблонах worker `testPort: "auto"`: перед запуском выбирается свободный
локальный порт и подставляется одновременно в `/TestClient -TPort` и
`/TestManager`. Поэтому независимые UI-пары разных агентов не конфликтуют с
уже работающим TestClient. Фиксированный порт указывай только когда он нужен
внешнему оркестратору.

Селекторы используют `objectName`, `title` и, для форм, `formName`, а не
экранные координаты. Отсутствующий критерий передаётся TestClient как
`Неопределено`, а не как фильтр по пустой строке. Поиск формы сначала проверяет
активное окно, затем приложение и остальные окна.
Перед `openNavigationLink` bridge запоминает уже открытые формы и принимает
только новую форму, совпавшую с `targetForm`. `attempts` означает число попыток
передать команду при её явном отклонении, а не число повторных открытий ссылки.
Ожидание выполняется штатным `ОжидатьОтображениеОбъекта()`, чтобы не обрывать
протокол TestClient частыми запросами во время тяжёлого `ПриОткрытии`. Интервал
для проверки `formName` задаётся `pollingInterval` (по умолчанию 5 секунд).

Открытие обычной обработки в ERP:

```json
{
  "action": "openDataProcessor",
  "metadataName": "ЕМС_РабочееМестоМенеджера",
  "formName": "Форма",
  "targetForm": {
    "title": "Рабочее место менеджера: ЕМС, Астра",
    "timeout": 90,
    "saveAs": "rmm"
  }
}
```

Для задачи, созданной в `before` гибридного сценария, передай UUID в
`openForm`. Это открывает форму через типизированную ссылку во временном
хранилище TestClient и не использует `e1cib/data/...`:

```json
{
  "action": "openForm",
  "metadataKind": "task",
  "metadataName": "ЗадачаИсполнителя",
  "uuid": "${active.Задача}",
  "formName": "ФормаЗадачи",
  "targetForm": {
    "formName": "Задача.ЗадачаИсполнителя.Форма.ФормаЗадачи",
    "timeout": 90,
    "saveAs": "task"
  }
}
```

Если требуются реквизиты и команды специальной формы выполнения задачи,
используй вместо двух шагов «открыть карточку + нажать декорацию» один:

```json
{
  "action": "openTaskExecutionForm",
  "metadataName": "ЗадачаИсполнителя",
  "uuid": "${active.Задача}",
  "targetForm": {
    "formName": "БизнесПроцесс.МойПроцесс.Форма.ФормаЗадачи",
    "timeout": 90,
    "saveAs": "review"
  }
}
```

После server hook для задач не используй `openNavigationLink`: на части
конфигураций он может разорвать связь TestManager/TestClient уже после
подстановки корректной ссылки. Для каталогов и документов этот путь остаётся
доступен.

Для документов, справочников, отчётов и общих форм используй `openForm`:

```json
{
  "action": "openForm",
  "metadataKind": "document",
  "metadataName": "ЗаказПоставщику",
  "formName": "ФормаДокумента",
  "targetForm": { "title": "Заказ поставщику", "timeout": 30, "saveAs": "order" }
}
```

`targetForm` всегда обязателен и должен содержать `formName`, `objectName` или
`title`. Для конкретной конфигурации предпочтителен устойчивый заголовок или
фактическое полное имя формы из `inspectUi`; это исключает ложный `passed`, когда
вместо цели открылась форма ошибки навигации.
На таймауте в результат шага добавляются дерево до навигации, доступные после
неё окна и формы; worker выносит их в `ui-diagnostics.json`. Сетевая ошибка не
подавляется и попадает в `Last transient TestClient error`.
Схема формата находится в `ui-scenario.schema.json`, пример —
`examples/native-ui-smoke.ui.json`.

Прямое открытие формы без меню:

```json
{
  "action": "openNavigationLink",
  "link": "e1cib/list/Документ.ПриемНаРаботу",
  "attempts": 3,
  "targetForm": {
    "title": "Приемы на работу",
    "timeout": 20,
    "saveAs": "hireList"
  }
}
```

Для объектной ссылки можно не вычислять `ref` вручную. Worker принимает UUID,
вид объекта и имя метаданных, валидирует их до запуска процессов и преобразует
UUID в порядок групп 4-5-3-2-1:

```json
{
  "action": "openNavigationLink",
  "kind": "catalog",
  "metadataName": "ВнутренниеДокументы",
  "uuid": "a14919f5-0dad-11e4-93f4-0050568b4127",
  "targetForm": {
    "formName": "Справочник.ВнутренниеДокументы.Форма.ФормаЭлемента",
    "timeout": 60
  }
}
```

В данном примере получится
`e1cib/data/Справочник.ВнутренниеДокументы?ref=93f40050568b412711e40dada14919f5`.

### Прогресс и артефакты

Worker печатает стадии `starting`, `startup`, `connect`, `running`, `waiting`,
`cleanup`, `passed` и `failed` с немедленным `flush`. При bridgeJob он раз в секунду читает
промежуточный результат и сообщает текущий шаг; для долгого ожидания раз в 10
секунд выводит heartbeat. Интервалы задаются `progressPollSeconds` и
`heartbeatIntervalSeconds`.

Тот же поток событий атомарно записывается в `progress.json`. Компактный итог
находится в `summary.json`, диагностические деревья — в
`ui-diagnostics.json`, а полный результат — в `worker.json`. Ошибка сценария
сохраняет исходную ошибку шага и не подменяется сообщением `ManagerFailure` при
нулевом коде завершения TestManager.

В начале нового запуска старые `summary.json`, `progress.json`, диагностика и
снимок удаляются, а `summary.json` сразу получает новый run ID со статусом
`starting`. Heartbeat содержит отдельно `stepElapsedSeconds` и общее время.
Консольный JSON принудительно выводится в UTF-8.

`client.py run-ui` по умолчанию печатает только компактный итог. Полный отчёт
сохраняй через `--report`; если он действительно нужен в stdout, добавь
`--full-output`.

### Выбор ссылочных значений

Основное действие для ИИ-агента — `selectReference`. Оно не присваивает полю
строку: выбор выполняется нативным API TestClient, поэтому в модели формы
устанавливается настоящая ссылка 1С.

`strategy: auto` последовательно пробует точный dropdown, type-ahead и, если
переданы `choiceForm`/`table`/`row`, форму выбора. Для dropdown и type-ahead
результат по умолчанию строго сравнивается с `expected` или `value`; это можно
отключить только явным `strict: false`.

Точное значение уже сформированного выпадающего списка:

```json
{
  "action": "selectReference",
  "form": "hire",
  "field": {"objectName": "Организация"},
  "strategy": "dropdownExact",
  "value": "Наша организация"
}
```

Эвристический ввод по строке с выбором первого сформированного значения:

```json
{
  "action": "selectReference",
  "form": "hire",
  "field": {"objectName": "Сотрудник"},
  "strategy": "typeAhead",
  "value": "Иванов Иван"
}
```

Выбор через отдельную форму списка:

```json
{
  "action": "selectReference",
  "form": "hire",
  "field": {"objectName": "Подразделение"},
  "strategy": "choiceForm",
  "choiceForm": {"formName": "Справочник.ПодразделенияОрганизаций.Форма.ФормаВыбора"},
  "table": {"objectName": "Список"},
  "row": {"Наименование": "Администрация"}
}
```

Для `choiceForm` исходная форма исключается из поиска новой формы. Затем bridge
строит `Соответствие` из `row`, вызывает `ПерейтиКСтроке()` и `Выбрать()` у
`ТестируемаяТаблицаФормы`. Ключи `row` могут содержать пробелы и точки.
`direction` может быть `both` (по умолчанию), `down` или `up`; поиск повторяется
`attempts` раз. Если ключи или доступные значения неизвестны, сначала вызови
`openChoice`, затем `inspectTable`, и используй полученную строку как образец.
Рабочий тест на реальной ЗУП —
`examples/zup-hire-reference-selection.ui.json`.

Ссылочная ячейка табличной части выбирается тем же действием, но с раздельными
селекторами целевой таблицы и таблицы формы выбора:

```json
{
  "action": "selectReference",
  "form": "document",
  "table": {"objectName": "Товары"},
  "row": {"НомерСтроки": "1"},
  "field": {"objectName": "ТоварыНоменклатура"},
  "strategy": "choiceForm",
  "choiceForm": {"formName": "Справочник.Номенклатура.Форма.ФормаВыбора"},
  "choiceTable": {"objectName": "Список"},
  "choiceRow": {"Наименование": "Тестовый товар"},
  "finishRow": true,
  "onChangeWait": 1
}
```

Bridge сам активирует `Товары` (это одновременно визуально переключает
страницу), находит строку, активирует ячейку, вызывает `ИзменитьСтроку()` и
`НачатьРедактированиеТекущейОбласти()`, открывает связанную форму выбора,
выбирает строку, вызывает `ЗакончитьРедактированиеСтроки(Ложь)` и ждёт обработку
`OnChange`. Для табличного `strategy: choiceForm` поля
`choiceTable`/`choiceRow` обязательны: старые `table`/`row` описывают цель.
Для обычного реквизита прежний контракт не изменился — `table`/`row` по-прежнему
описывают форму выбора.

Текстовую ячейку меняй через `inputTableCell`, а проверяй через табличный
вариант `assertField`:

```json
{
  "action": "inputTableCell",
  "form": "document",
  "table": {"objectName": "Товары"},
  "row": {"НомерСтроки": "1"},
  "field": {"objectName": "ТоварыКоличество"},
  "value": "2",
  "replace": true,
  "onChangeWait": 1
}
```

```json
{
  "action": "assertField",
  "form": "document",
  "table": {"objectName": "Товары"},
  "row": {"НомерСтроки": "1"},
  "field": {"objectName": "ТоварыКоличество"},
  "expected": "2"
}
```

Табличный `openChoice` полезен для разведки: он входит в редактирование и
оставляет строку открытой, чтобы следующие `inspectTable`/`selectTableRow`
отработали отдельно. Для рабочего атомарного сценария используй
`selectReference`.

Пример безопасного закрытия изменённой формы:

```json
{
  "action": "closeForm",
  "form": "hire",
  "onPrompt": "discard",
  "waitClosed": true,
  "timeout": 20
}
```

### UI Automation fallback

Если рабочая форма 1С не публикует дерево `ТестируемаяФорма`, сценарий может
содержать `uiaSteps`. Worker выполняет их после штатных шагов `/TestManager` на
том же скрытом Windows desktop. Для редких стартовых диалогов допускается
`uiaBeforeSteps`: эти шаги выполняются после запуска TestClient, но до запуска
TestManager. Используй `uiaBeforeSteps` только для безопасного bootstrap
окружения; в конфигурациях БСП вмешательство до подключения TestManager может
нарушить рукопожатие `/TestClient`.

Поддерживаются `inspect`, `wait`, `invoke`, `click`, `clickWindow`, `setValue`,
`typeText`, `typeTextWindow`, `pasteTextWindow`, `pressKey`, `pressKeyWindow`,
`toggle` и `sleep`.

Селектор задаётся полями `name` (допускает `*` и `?`), `controlType` и
`occurrence`. Для составного контрола `click` принимает `relativeX` и
`relativeY` от `0` до `1`. `click` отправляет полный набор оконных mouse-событий
без переключения пользовательского desktop; `captureOnFinish` сохраняет снимок
окна через `PrintWindow`.

Для ссылочных полей 1С одного UIA `setValue` недостаточно: ValuePattern способен
изменить отображаемый текст, не выбрав объект в модели формы. Используй
`selectReference`. Для `strategy: choiceForm` bridge вызывает штатный
`Поле.Выбрать()` у активного редактора ячейки: открытая форма сохраняет владельца
выбора и возвращает ссылку в табличную часть. Отдельное открытие списка по
метаданным для рабочего выбора не подходит, потому что такая форма не связана с
редактируемой строкой.

Минимальный результат:

```json
{
  "ok": true,
  "name": "Приём сотрудника",
  "count": 12,
  "status": "passed"
}
```

Если JSON содержит `"ok": false`, worker помечает запуск неуспешным даже при
нулевом коде процесса 1С. Отсутствие результата в bridge job считается ошибкой
контракта встроенного менеджера. Файловый `resultTransport: file` оставлен только
для пользовательских менеджеров и тестирования самого worker.

## Изоляция и безопасность

- Windows desktop никогда не переключается на пользовательский.
- По таймауту менеджер и клиент принудительно завершаются.
- Аргументы после `/P`, `--password`, `--token` маскируются в отчёте. Список
  настраивается через `secretFlags`.
- Конфигурацию worker следует хранить локально, если она содержит пароли.
- Механизм не отменяет лицензирование тонкого/толстого клиента 1С, но переносит
  клиентский сеанс на выделенный worker и не требует лицензии web-клиента.

## UUID-ссылки, инспекция и тёплый batch

Ссылочное значение задавай UUID, а не отображаемым текстом. Worker обращается к
bridge целевой базы (`targetBridgeBaseUrl`, в same-db допускается
`bridgeBaseUrl`), получает актуальное представление и компилирует штатный
контракт выбора:

```json
{
  "action": "selectReference",
  "field": {"objectName": "Организация"},
  "strategy": "choiceForm",
  "choiceForm": {"formName": "Справочник.Организации.ФормаВыбора"},
  "table": {"objectName": "Список"},
  "reference": {
    "kind": "catalog",
    "metadataName": "Организации",
    "uuid": "00000000-0000-0000-0000-000000000000"
  }
}
```

Если колонка представления называется иначе, укажи `choiceField` внутри
`reference`. UUID остаётся источником идентичности; представление используется
только штатной формой выбора TestClient.

Для разведки формы агентом:

```powershell
python .\client.py ui-inspect .\local.worker.json --uuid $uuid --kind document --metadata-name ДокументТеста --artifact-dir .\artifacts\inspect
```

Команда возвращает компактные `screens/elements/tables/columns` и рекомендуемые
селекторы. Приоритет: `objectName`, затем `formName`, затем `title`. Строгий поиск
в 1С дополняется однозначным нормализованным совпадением регистра и пробелов;
неоднозначность считается ошибкой. Каждый неуспешный отчёт содержит
`agentDiagnostics.category/nextAction`, а полный `agentUi` остаётся в report.

`run-ui-suite` выполняет UI-сценарии последовательно в одной скрытой сессии
TestClient/TestManager, сохраняя отдельный результат каждого сценария. Можно
передать файлы и/или каталог; каталог рекурсивно ищет `*.ui.json`:

```powershell
python .\client.py run-ui-suite worker.json .\ui-scenarios --artifact-dir .\artifacts\ui-suite --report .\artifacts\ui-suite\report.json --junit .\artifacts\ui-suite\junit.xml
```

После сценария bridge закрывает только открытые им формы и сбрасывает ссылки
на формы. При ошибке сохраняется диагностика сценария; `--fail-fast` останавливает
набор после первой ошибки. `run-ui-batch` оставлен как совместимый псевдоним.
убирает повторный запуск платформы. Сценарии в batch должны оставлять UI в
предсказуемом состоянии (обычно завершаться `closeForm`).
